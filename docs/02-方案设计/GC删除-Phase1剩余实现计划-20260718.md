# GC 删除 Phase 1 剩余实现计划

- 日期：2026-07-18
- 前置：`GC-DELETE-SPIKE-0001`、`GC-DELETE-PHASE1-BE-0001` 增量 1
- 范围：维护窗口、tenant-only、MinIO exact VersionId 删除
- 本文性质：后续拆包计划，不包含删除实现

## 1. 已建立的地基

增量 1 只建立 GC 控制表、引用 coverage gate、稳定 schema fingerprint、逐对象证据和
双扫观察状态机。扫描不会删除对象或业务记录；默认命令仍是 dry-run，只有显式
`--record-candidates` 才写 GC 控制表。

当前安全边界：

1. 业务引用面由反射发现，并由经审查的 schema digest 门禁；schema 漂移即 fail closed。
2. GC 自身 locator 显式分类为 `gc_control`，接受 tenant/key 校验但不保护自己。
3. 只有 canonical `tenants/{tenant_id}/...` 且租户存在的对象可进入观察。
4. catalog、路径穿越、未知租户和跨租户 key 永不 eligible。
5. 首次发现满 7 天、至少两个不同 scan、干净扫描间隔满 24 小时才 eligible。
6. 没有 VersionId 的对象只能 `skipped/object_identity_unavailable`。

以下 PR 必须按顺序合入。任何一步失败都不能通过 `--force` 绕过。

## 2. PR 依赖顺序

### PR 2：审批与审计控制面

**目标**：只允许平台管理员审批已经 eligible 的候选；仍不删对象。

实现：

- 管理员按 `candidate_id[] + scan_id` 审批；CLI/API 不接受任意 bucket/key。
- 同一 tenant 一批，按 `(bucket, key)` 排序锁候选行。
- 审批时固化 schema fingerprint、对象 identity、逐对象 evidence 和审批过期时间。
- 任一候选非 eligible、证据缺失、tenant 混批或 fingerprint 不同，整批不变更。
- `eligible -> approved` 与 `gc_audit_log` 同事务写入；普通日志只记 key hash。
- GC 查询端点仅平台管理员可访问，明文 key 不进入通用任务/分析接口。

承重门：

- 非管理员 403；跨租户 404；raw key 审批参数 422。
- 两管理员并发审批只有一个状态转换，审计恰好一条。
- 任一候选 stale 时整批回滚。
- schema fingerprint 或 VersionId 在审批前变化时不得 approved。
- 审计明文 key 仅存在 `gc_audit_log`，结构化普通日志只有 hash。

待定：审批有效期建议 24 小时；维护窗口未开始前允许撤销 approved。

### PR 3：维护冻结协议与可验证凭证

**目标**：把“已停写、队列已排空、worker 已停”变成 final-proof 可验证的持久事实。

建议机制：

1. 新增全局维护状态及一次性 `freeze_epoch`。先由共享 API dependency 拒绝所有媒体写入
   和任务生产，读接口保留；Celery beat/producer 同样检查该 epoch。
2. 入口冻结后让现有 worker 排空，检查 Redis 中 `default/avatar/image/video` 等实际队列、
   Celery active/reserved/scheduled、数据库 queued/running 媒体任务和 reserved usage。
3. 排空后停止 beat、全部媒体 worker 和 API 写实例；部署脚本验证相关容器均已停止。
4. app/worker PostgreSQL 角色切为默认只读并断开旧连接；GC one-shot 使用独立最小权限角色。
5. 生成有短有效期的 freeze certificate，记录 epoch、部署 revision、队列快照、DB 快照、
   停止实例清单、操作者和配置 fingerprint。任一检查 unknown 即不签发。
6. final-proof 与 runner 每次 claim 都验证同一未过期 epoch；解除维护即让未完成 job 回到
   `needs_revalidation`，不得在线自动续跑。

必须覆盖的写入源：API、Celery producer、普通 worker、beat、恢复任务、启动 seed、运维脚本、
管理员重试入口。仅停 Nginx 或仅停 worker 都不构成冻结证明。

承重门：

- 任一队列非空、active/reserved/scheduled 非空、queued/running 任务存在、app 写连接存在、
  worker/API 未停或 epoch 过期，均拒绝签发。
- 冻结后从 API、producer、worker、beat 和运维入口写媒体引用都失败。
- 解除冻结或部署 revision 改变后旧 certificate 失效。
- 真 PostgreSQL + Redis 双进程测试证明旧连接不能越过冻结。

待定：生产以 Docker Compose 为准还是先抽象 orchestration adapter；队列全集应从 Celery
配置发现，不能另建易漂移白名单。对象存储的人工作业账号需由运维 RBAC 保证在窗口内停写。

### PR 4：整批 final-proof 与 durable intent

**目标**：在冻结窗口内重做完整证明，并只创建 durable reclamation jobs；仍不删对象。

事务顺序：

1. 校验 freeze certificate，按 `(bucket, key)` 排序 `FOR UPDATE` 锁 approved 候选。
2. 校验审批未过期、tenant 单一、schema fingerprint 与当前 coverage 完全一致。
3. 一次批量重跑全部 protective 引用面；任一 reference/coverage/query 异常则整批失败。
4. 校验外部 lease、队列排空和冻结 epoch 未变化。
5. 对每个对象 HEAD，比对 bucket/config fingerprint、exact VersionId、ETag、size、last-modified。
6. 若同时回收业务记录，记录变更与 jobs 必须在本事务内；插入 durable jobs 后提交。
7. commit 前后均不调用 object delete，也不发布一次性 Celery 消息。

承重门：

- 任一候选证明失败，整批没有 job、没有业务记录变更、没有 storage 调用。
- reference 在审批后出现、VersionId/ETag 变化、fingerprint 变化、freeze epoch 变化均 fail closed。
- 记录删除与 jobs 中途抛错时整批回滚。
- 多批并发使用稳定排序，无死锁；同 candidate 只产生一个 intent。

待定：首版批量上限建议 100；Asset/VideoTask 等记录驱动回收另开按业务所有权划分的适配 PR，
不得在 GC 服务里猜测跨表删除规则。

### PR 5：VersionId 存储协议与 MinIO 预检

**目标**：提供 exact-version 删除原语，但不接 runner。

实现：

- 扩展 `ObjectStorage` 为显式 `head_identity` 与 `delete_exact_version`，删除参数必须包含
  tenant、bucket/config fingerprint、key、VersionId；不保留仅 key 的 GC 后门。
- S3/MinIO 调用 `delete_object(Bucket, Key, VersionId)`；返回值和后续 HEAD/list-version 用于确认。
- Local backend 在 GC 删除路径 fail closed，不伪造 VersionId。
- 部署预检验证目标 bucket 已启用 versioning，HEAD 能读回非 `null` VersionId，测试对象的旧版
  精确删除不会删除新版本。预检未通过则生产只允许 dry-run/observe。

承重门：

- VersionId 缺失或变化时 delete client 调用次数为 0。
- key 穿越、catalog、tenant mismatch、bucket/config mismatch 时调用次数为 0。
- 专用 MinIO 测试桶验证覆盖同 key 后删除旧 VersionId，新版仍可读。
- 所有常规单测 mock storage；不触碰生产桶。

待定：MinIO delete marker 与删除旧版本后的“成功”确认口径；S3 兼容实现是否都返回
`VersionId`。结论未验证前不能接 runner。

### PR 6：Transactional outbox 与维护窗口 one-shot runner

**目标**：消费已提交的 reclamation jobs，完成首个可审查的真删路径。

实现：

- `gc_reclamation_jobs` 本身作为 durable outbox；不在事务 commit 后只 publish 一次 Celery。
- one-shot runner 仅在有效 freeze epoch 内启动，使用 `FOR UPDATE SKIP LOCKED` claim。
- claim 后再次校验 candidate/job/tenant/key/fingerprint/freeze/VersionId，再调用
  `delete_exact_version`；数据库先提交 intent，对象删除在后。
- 对象已不存在且能够证明目标 exact VersionId 已删除时按幂等成功收敛。
- 每次状态变更与 `gc_audit_log` 同事务；普通日志只记 job ID、key hash、error code。
- runner 在本批所有物理尝试完成后退出，不复用普通媒体 worker。

承重门：

- DB intent commit 失败时 storage delete 为 0。
- commit 后 storage 失败时 job 可恢复且对象仍在。
- 对象删除成功、状态提交失败后重跑可幂等收敛，不误删同 key 新版本。
- 两 runner 并发不重复 claim；VersionId 在 claim 前变化时 skip。
- 跨租户、穿越、catalog 永不调用 delete。
- 维护窗口解除时 runner 立即停止，未完成项必须重新审批和 final-proof。

### PR 7：重试、死信、告警与上线演练

**目标**：把失败收敛和人工兜底做完整，再允许生产维护窗口使用。

实现：

- transient 失败最多 3 次指数退避；仅在同一有效 freeze epoch 内执行。
- AccessDenied、版本化关闭、bucket/config 错等 permanent 错误直接 dead-letter。
- dead-letter 保存 job/candidate、key hash、受控明文 key、fingerprint、error code、actor；告警
  只含 hash，不含凭据、presigned URL 或响应正文。
- 平台管理员只能按 dead-letter/job ID 重新审批，不能修改 key/VersionId 后强行重试。
- 专用测试桶做完整演练：覆盖版本、制造 transient、状态提交失败、恢复和审计导出。

承重门：

- 第 1/2 次 transient 进入 retry_wait，第 3 次后 dead_letter，退避时间可验证。
- permanent 首次即 dead_letter；离开维护窗口不自动 retry。
- 审计链可从 approval 追到 final-proof、每次 attempt 和最终结果。
- gitleaks、全量 ruff/pytest、专用 MinIO 集成、故障注入演练全部通过。

## 3. 上线硬门

生产启用前必须同时满足：

1. MinIO bucket versioning 已开启，预检读到非空 VersionId。
2. 冻结脚本能一条命令进入、证明、执行、退出维护窗口，并有失败回滚手册。
3. 所有媒体写入源均纳入冻结 coverage；未知写入源等同失败。
4. dry-run 候选人工抽验通过，首批限制为单 tenant、小批量。
5. 备份、告警、dead-letter 管理员流程和审计保留策略已验收。
6. runner 独立 PR 经最高等级审查后才允许合入；此前所有环境保持零真删。
